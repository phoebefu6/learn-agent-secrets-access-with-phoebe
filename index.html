The six sessions 🧭 · from one shared admin key to a plan a reviewer can sign

The running case is Halyard, a constructed logistics SaaS. Its ops agent reads support tickets and customer email, queries the analytics warehouse, issues refunds up to a limit, posts to team chat and fetches the tracking pages customers paste in. On day one every tool reads one shared admin key from an environment variable. Halyard, its tools, people and weights are invented for teaching, and every page says so.

🗝️ Session 1 · foundations

What the agent is holding

The agent as a non-human identity, the five places its key ends up, why one shared admin key ships first and what it costs, and the first blast-radius count on Halyard's day-one setup.

▶ Start here 🪪 Session 2 · core

Whose authority: the agent's own, or the user's

Service identity against acting for a person, delegated OAuth and token exchange with actor and subject, the confused deputy drawn as a mechanism, and an identity map for every Halyard tool.

identity map ✂️ Session 3 · core and bench

Scope the tool, not the agent

One credential per tool, read and write split, fine-grained scopes from the real GitHub, Slack and Google lists, expiry and audience, and the bench cut tool by tool.

★ the bench 🔐 Session 4 · deeper

Keep the key out of the context window

Credential brokers that attach the token at call time, short-lived dynamic secrets, redaction in traces, and MCP authorization: the server as resource server, audience-bound tokens, no passthrough.

broker design ✋ Session 5 · deeper

When the agent must ask first

The lethal trifecta, approval gates for irreversible and high-value actions, and injection-resistant designs taught as a live disagreement, with approval fatigue as the counter-argument.

gate rules 🧾 Session 6 · capstone

Prove what it did, then sign the plan

Attributable audit records, revocation and the kill switch, the full bench ladder from shared admin key to finished design, and Halyard's agent access plan on one page.
