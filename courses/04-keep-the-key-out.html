Learn Secrets & Access for AI Agents with Phoebe · Session 4 of 6

Keep the key out of the context window

After session 3 every Halyard tool holds a key cut to its job. Those keys still sit where the model can be talked into repeating them: in the environment of a process whose errors flow back into the context, in the traces, on the provider's side. Tonight we move them below the line the model reads. A broker attaches each key at call time, secrets are leased for an hour instead of held forever, traces are redacted before they are written, and the MCP server becomes an OAuth resource server that accepts only tokens issued to it.

Part 1 · covers credential brokers and proxies

A broker attaches the key at call time

5 min live

The model does not need the key. It needs the result of a call that used the key. A broker splits those two: the model emits a tool call with a tool name and arguments and nothing else, and the component that actually talks to the API looks up who is calling, fetches or mints a token, attaches it to the outbound request and strips it from what comes back. The context window becomes a boundary the key never crosses.

LiveWhat a broker does2 min▶

It holds the keys. Or better, it holds the right to mint them: it asks a secret store or a token issuer for a credential when a call needs one. The agent process, its prompt and its tool results never see the value.

It attaches per call. The model emits refunds.issue with an order id and an amount. The broker decides which identity that call runs as, fetches the token for that identity, and puts it in the Authorization header of the outbound request. One call, one attachment.

It never returns them. On the way back it drops credential headers and redacts anything that looks like a key in the response body, including error text. Session 1's place 3, the 401 error that printed the key prefix, is closed here or nowhere.

It can enforce more than the key. Because every call passes through it, the broker is a natural place to pin scope per tool, cap the rate, and write the audit record session 6 designs. None of that needs the model's cooperation.

LiveWhy it does not shrink what the agent can do2 min▶

Be honest about what moves. A broker changes where the key is, not what the key allows. A poisoned ticket that steers the agent to send an email still gets the email sent, because the broker faithfully attaches the tickets key to a call the model chose. So on the bench, moving from rung 2 to rung 3 leaves the headline at 6 and the weighted blast radius at 26.

What falls is what a leak is worth. With keys in the agent's environment, a stolen copy of any one reaches actions directly, with no agent and no gate in the way: the bench prints 5. Behind a broker there is nothing in reach to steal: 0. And the keys readable in the context fall from 4 to 0. Those are different attacks from the headline's, and you need both numbers.

Shrinking what the agent can reach was session 3 (scopes). Putting a person in front of what is left is session 5 (gates).

Self-studyWhere the broker runs3 min▶

Inside each MCP server. Each tool's server holds the right to its own credential and nothing else. The blast radius of compromising one server is one tool's key. The cost is that every server team implements fetching, attaching, stripping and redaction, and they will do it slightly differently.

A gateway in front of several servers. One component attaches credentials for every upstream, so the strip and redaction logic exists once and is tested once. The cost is a single component that can mint every tool's token: you have rebuilt a concentration of power, and it needs the same scrutiny the shared admin key should have had.

Either way, the rule that matters is the same: the token the broker attaches is the broker's own credential for the upstream, never something the client handed in. Part 3 shows why the MCP specification makes that a MUST. How to rotate the long-lived root credentials a broker or vault itself depends on is covered in learn-data-access-control, secrets and keys.

Real world

The MCP specification already draws this line. Its security considerations for authorization (revision 2026-07-28, read 2026-11-10) say that when an MCP server calls an upstream API it needs a separate token for that upstream, and that the server MUST NOT pass through the token the client sent it. A broker is that rule turned into a component: the client's token gets the call into the server, and the server's own credential gets the call out.

Part 2 · covers dynamic, short-lived secrets and redaction in traces

Short-lived secrets, and traces that cannot leak them

5 min live

A broker keeps the key out of the context. Two more places from session 1 remain: a key that leaks anyway should stop working soon, and the trace store should never hold one at all. Leases handle the first: the credential is minted for a request and dies on a timer. Redaction handles the second, and it has to happen before the write, because a trace store is searchable by everyone on call.

LiveLeases: what Vault actually guarantees2 min▶

HashiCorp Vault's lease and database documentation (read at source 2026-11-10) is the clearest public description of the mechanism, so we use its words.

  • Every dynamic secret has a lease, and Vault returns a lease id with it. Static key-value secrets do not.
  • The TTL is the lease's duration. Before it runs out you renew, or you request a new secret. A renewal counts from now, not from the original expiry.
  • Revocation is immediate. Revoking a token also revokes every lease created with it, and a prefix revoke such as vault lease revoke -prefix aws/ kills a whole group.
  • The database engine creates a unique username and password on each request. The tutorial's example role uses default_ttl=1h and max_ttl=24h.

For an agent this means two things. A credential that leaks through some path you missed is worth at most its remaining TTL. And because each request has its own user, compromising one consumer means revoking its credentials only, not rotating something everyone shares.

LiveRedaction rules that hold up2 min▶

Redact before write, not after. A nightly scrub job leaves a window in which the key is searchable, replicated and backed up. The redaction step sits in the pipeline between the span and the store.

Match two ways. By name: header and field names you know carry secrets, such as Authorization, Cookie, Set-Cookie, and any field named token, secret or key. By pattern: the prefixes your keys use, such as hx_live_, and the provider prefixes you hold, such as Stripe's rk_ and sk_. Names catch structured data; patterns catch the key that turns up inside an error string.

Test with a canary. A redaction rule you never tested is a rule you hope works. Plant an obviously fake key in a test call, in a header and in an error body, then search the store for it. The expected hit count is zero, and any hit is an alert. OWASP's LLM02:2025 lists tokenization and redaction among its prevention groups for sensitive information disclosure; the canary is how you know yours is on.

LiveThe provider side: what is not in the context is not sent1 min▶

Place 5 has no redaction step you control: everything in the context window goes to the model provider on every turn, under whatever retention terms your contract sets. The only reliable fix is upstream of the request. With the broker in place no key is in the context, so no key is sent. Redaction of tool results in the broker (Part 1, step 4) is what keeps that true when a tool fails noisily.

Self-studyVendor walkthroughs, as claims with their basis3 min▶

Setting up a Vault database secrets engine, a cloud provider's workload identity or an identity product's agent features is outside the 45 minutes. When you read those guides, sort each claim by its basis:

  • Mechanism you can check in the product's own reference: lease ids, TTLs, revoke semantics. The Vault facts above are of this kind.
  • A default you should verify in your own deployment: TTL values in tutorials are examples, not recommendations for your workload.
  • A vendor's description of its own product's safety: useful, but not independent evidence. Ask what the claim is measured against.

None of those walkthroughs were run for this page; the snippets on it are read and edited, never deployed against a real service.

Real world

One request, one database user. Vault's database secrets tutorial (read 2026-11-10) has the engine create a fresh username and password each time an application asks, under a role whose example lease is one hour, renewable to at most a day. Its point for Halyard: if the warehouse tool's credential turns up somewhere it should not, you revoke that one lease, and every other consumer keeps working.

Part 3 · covers MCP authorization

MCP authorization: the server is a resource server

5 min live

So far the broker's job has been the outbound side. MCP authorization is the inbound side: how a client proves it may call the MCP server at all. The specification (revision 2026-07-28, read at source 2026-11-10) makes the server an OAuth 2.1 resource server and adds two rules that matter for agents more than anything else on the page: the token must be issued for this server, and the server must never forward it.

One more for agents: when a token lacks a scope, the server answers 403 with error="insufficient_scope" and the client does step-up authorization for the extra scope. That is the protocol's version of session 3's advice: start small and ask for more when you need it.

LiveToken passthrough, and the four things it breaks2 min▶

The specification's security best practices define token passthrough as an MCP server accepting a client's token that was not issued to it and forwarding it downstream, and forbid it. The listed risks, read at source:

  • Security control circumvention. The upstream's rate limits, validation and monitoring assume the token was issued for it. A forwarded token skips the server's own controls on the way.
  • Accountability and audit trail. The upstream logs the client's identity, not the server's, so you cannot tell which server made the call. Session 6 needs that answer.
  • Trust boundary. A token that works at several services turns one compromised server into access to all of them.
  • Future compatibility. Controls added to the server later have no effect on calls that never really went through it.

For Halyard: the refunds MCP server must reach payments with its own credential for payments, attached by the broker, never with the token the agent host used to reach the refunds server.

Self-studyOAuth 2.1: still a draft, and the specification cites an older one3 min▶

MCP authorization is built on OAuth 2.1, which is an Internet-Draft, not a standard. The MCP revision 2026-07-28 cites draft -13; the latest on the IETF datatracker when this page was checked is draft-ietf-oauth-v2-1-17, dated 31 October 2026. Drafts, not standards: the text can still change.

  • PKCE is required for every authorization code flow.
  • The implicit grant is removed, and the resource owner password credentials grant is not specified.
  • Redirect URIs must match exactly a registered one (a loopback port is exempt).
  • Refresh tokens are bound to the scope and resource servers the owner consented to.
  • Sender-constraining is a SHOULD: DPoP or mutual TLS, so a copied access token is not usable by whoever copied it.

What was not confirmed in the portion read: the exact refresh-token one-time-use wording. Check it in the current draft rather than in a summary.

Re-verify the specification before you deliver this. The MCP specification and the OAuth 2.1 draft both change several times a year. Before you teach or build from this page, open the MCP versioning page, confirm the current revision is still 2026-07-28, and check the latest OAuth 2.1 draft number. If either moved, re-read the authorization section before trusting the table above.

Real world

Audience is what makes a token single-purpose. RFC 8707's resource parameter lets the client tell the authorization server which resource the token is for, and the MCP specification requires the client to send it, set to the MCP server's canonical URI, even when the authorization server does not support it. Combined with the server's MUST to validate audience, a token stolen from Halyard's tickets server is refused at the refunds server.

Two numbers, two attacks. The headline counts what a poisoned input can steer the agent to do. The stolen-key number counts what someone holding a copy of a key can do with no agent at all. A broker is the cheapest way to drive the second to zero, and it does nothing for the first. If a review only reports one of them, ask for the other.

Homework

Before session 5

30 min
  1. Find your broker. For each tool of your own agent, write where the key is attached today: in the agent's process, in the MCP server, or in a gateway. Every "agent's process" is a key the model can be talked into printing.
  2. Force an error. Make one tool fail on purpose (a wrong password, a bad host) and read exactly what comes back into the context. Write down anything that looks like a credential, a connection string or a key prefix.
  3. Run a canary. Put an obviously fake key in one test call and search your trace store and transcripts for it the next day. Record the hit count.
  4. Check one MCP server for passthrough. For one HTTP MCP server you run, find the code that calls upstream and write down whose token it sends. If it is the client's, that is the first fix.
Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · Moving Halyard from rung 2 to rung 3, the bench headline stays at 6. Why is rung 3 still worth doing?

The headline measures what a poisoned input can steer the agent to do, and the broker attaches the same scoped keys to whatever the model calls, so it stays at 6. What falls is the other attack: a copied key used directly. B is a guardrail, not a broker. D was session 3's work.

2 · An MCP server validates that every token's audience is itself, and reaches its upstream API only with its own token. What does that pair prevent?

Audience validation binds a token to one server; no passthrough stops it going further, which keeps the upstream's controls and logs meaningful. Neither touches injection (B). PKCE is still a MUST (C), and audience says where a token works, not what it may do there (D).

3 · Of session 1's five places a key ends up, which does a redaction step before write close, and what else does keeping keys out of the context close?

Redaction in the trace pipeline closes place 4. Place 5 has no filter you control, so the only fix is upstream: the broker keeps keys out of the context, so nothing reaches the provider. The environment (A, B) is where a key legitimately belongs, and now it is the broker's, not the agent's.
