Part 1 · covers attributable audit records

An audit record that names the agent and the person

5 min live

On day one, every log line said HALYARD_ADMIN_KEY did it. A record a reviewer can use answers six questions, and the design work is making sure each answer comes from a system that already knows it, not from the agent's own account of what it did.

LiveThe six fields, and where each one comes from3 min▶

Agent id from the workload identity the agent authenticated with (session 2), not a name in its prompt. Human principal from the delegated token: RFC 8693 puts the person in the subject and the agent in the act claim, and nested act claims record the chain when one agent calls another. For batch work with no person, the field says so explicitly. Token id from the broker that minted or attached the short-lived token (session 4), so one record can be tied to one lease and one revocation.

Tool and argument hash from the MCP server that executed the call. Hash the arguments rather than storing them: the record proves exactly what was sent without copying a customer's address or a refund note into a log that more people can read. Keep the clear arguments, if you must, in a store with its own access rule. Approver from the gate (session 5), with the time, or "not gated".

Self-studyWhy passthrough breaks the record2 min▶

The MCP security best practices (revision 2026-07-28, read at source) forbid token passthrough, where an MCP server accepts a token that was not issued to it and forwards it downstream, and list the risks. One of them is accountability and audit trail issues: the downstream system sees the client's token and cannot tell that the MCP server, or the agent behind it, made the call. A record that has to name the agent needs every hop to present its own token for its own audience, which is what session 4 built.

OWASP's LLM06 Excessive Agency entry is blunt about the limits of what this buys: logging, monitoring and rate limiting limit the damage, they do not prevent it. The audit record is how you find out and how you prove; the scopes, broker and gates are what stopped it happening.

Real world

The standards bodies are writing this field down. The IETF individual draft "OAuth 2.0 Extension: On-Behalf-Of User Authorization for AI Agents" (draft -02, 2025-08-25, now expired) names auditability as a goal, carried by token claims that record the user, the client and the agent. A later draft, "AI Agent Authentication and Authorization" (draft-klrc-aiagent-auth-03, 2026-07-06), was adopted by the IETF WIMSE working group. Both are drafts, not standards; the claim structure they lean on, RFC 8693's act, is a published standard you can use today.

Part 2 · covers revocation and the kill switch

Three speeds of stop

5 min live

Day one, stopping the agent meant revoking the shared key and breaking six systems, so nobody would. With one identity, per-tool keys and short leases there are three levers, each faster and blunter than the last. Write down in advance who may pull each one.

LiveLeases make revocation a command, not a project3 min▶

HashiCorp Vault's documentation (read 2026-11-10) describes the mechanism the first two levers rely on. Every dynamic secret has a lease with an id and a time to live; revocation invalidates it immediately; revoking a token revokes every lease created with it; and vault lease revoke -prefix revokes a whole group, the example being everything under aws/. The database engine creates a unique username and password on each request, so a compromise means revoking one application's credentials, not rotating a shared one.

Short leases are also the lever you do not have to pull. Vault's database tutorial uses a default time to live of one hour and a maximum of 24 hours as its example; a token that leaked at 14:00 is useless by the time anyone reads the log. Pick your own numbers; the point is that they exist.

Self-studyThe kill switch, and the offboarding it leads to2 min▶

The kill switch lives at the broker because the broker is the only place every tool's token comes from. Disable the agent's identity there and nothing new is minted; with leases measured in minutes, the agent is out of every system within one lease. It must fail closed: a tool that cannot get a token refuses the call and says why, it does not fall back to a cached key.

Retiring the agent for good is the same switch plus cleanup, and the step teams forget. OWASP's NHI1:2025 Improper Offboarding is exactly that: non-human identities left active after their job ends. Put the retirement steps in the plan now, while someone remembers what the agent holds.

Part 3 · covers the full blast-radius ladder

The whole ladder, computed

5 min live

Every rung from sessions 1 to 5, run through the same graph search. The table below is computed by the engine as the page loads; the drawing beside it uses the same numbers. Read it for the shape: which rung moved the headline, which moved something else, and which did nothing to the count but still earned its place.

LiveReading the ladder honestly3 min▶

Scopes did most of it. Going from one broad key per tool to the scopes each job needs took the headline from 15 to 6 and the weighted radius from 90 to 26. That is the cheapest rung: no new infrastructure, only a list of scopes per tool.

The broker did not move the count, and it is not optional. With keys behind a broker the headline stays at 6, because the agent can still do everything its scopes allow. What changes is the stolen-key column, from 5 to 0, and keys readable in the context, from 4 to 0. A review that only reads the headline would cut this rung; an incident is exactly when it matters.

Gates broke the trifecta. Gating the three irreversible actions still reachable (send email, refund, fetch) took the headline to 3 and left no ungated way out, so private data can be read but not sent anywhere. On-behalf-of removed the last payments read from the agent's own identity: 2 left, both reads.

Two is not zero, and should not be. The agent's job is to read the support inbox and the team channel. A design that reached zero would be an agent that cannot do its work. The finished number is the residual risk you accept and write down, with the gates and the audit record as the controls around it.

Build-along

Break the finished design, then sign the plan

★ 22 min · everyone builds

The bench starts on rung 5, the finished design. Before anyone signs, break it twice the way real systems drift, read what the search prints, and write the two lines into the plan that would have caught each. Then assemble the six pages into one.

Confirm the finished numbers. On rung 5 the bench prints 2 of 19 sensitive actions reachable with no human in the way, weighted 8, a stolen key reaching 0, no keys readable in the context, 2 approvals and the trifecta broken. The shortest path left is ticket body, ops agent, tickets tool, read the support inbox.

Break 1: tick "Rep requests also read the ticket text". A rep asks the agent in chat to sort out ticket 4471, and the agent opens the ticket in the same run. The headline goes to 3, weighted 11: read charges is back, now under the rep's delegated authority. On-behalf-of caps reach at what the rep may do; it does not stop injection from riding along.

★ Step 2 · plan line that catches itRep requests name an order id. The agent does not load ticket text into a run that carries a rep's delegated token. Where it must, the run drops to the agent's own identity first.

Break 2: untick it, tick "The warehouse tool keeps its admin role". Someone restored the old role "to fix a dashboard". The headline goes to 3, weighted 15: the customer contact table is reachable from a poisoned ticket, and the gates now ask for 4 approvals instead of 2. Nothing in the agent changed; one role did.

Homework

After the last session

45 min
  1. Write your own one-page plan. Same nine lines, for your agent, with your own residual-risk count. If you cannot fill a line, that line is your next piece of work.
  2. Pull one audit record. Find a real tool call your agent made last week and try to fill the six fields from your systems alone. Note every field you had to guess.
  3. Time the kill switch. In a test environment, disable the agent's identity and measure how long until every tool refuses. If the answer is "until the key is rotated", you do not have a kill switch yet.
  4. Book the red team. Send them the plan, not the prompt, and ask them to break the residual list first.
Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · Which source should fill the "human principal" field of an audit record for a refund the agent made at a rep's request?

The token was issued by the authorization server to that rep and that agent, so it is the one source the agent cannot talk its way into. A and B are text the model or a user wrote; C names nobody in particular.

2 · On the ladder, putting Halyard's keys behind a broker (rung 3) leaves the headline at 6. Why keep the rung?

The weighted radius stays at 26 too, so A is wrong. The broker changes what a leak is worth: nothing in the context can leave with a request and be used directly. Gates are a separate rung.

3 · On the finished design, the warehouse tool quietly gets its admin role back. What does the bench report?

Export and drop are irreversible, so they are gated and the trifecta stays broken; but reading the customer table is not irreversible, so no gate stops it. One role change undid one rung, which is why the plan pins scopes and re-runs the check on any change.
