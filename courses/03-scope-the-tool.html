Scope the tool, not the agent

An agent does not need permissions. Its tools do, and each tool needs only what its one job needs. Tonight we take the key away from the agent and give one to each tool, read the scope lists Gmail, Slack and GitHub actually publish to find the rung each tool should sit on, add the two fields most scope tables forget, expiry and audience, and then cut Halyard's blast radius tool by tool on the bench, watching which cut buys the most.

Part 1 · covers one credential per tool and the read and write split

One credential per tool

5 min live

When the agent holds the key, the key has to cover everything any tool might do, so every tool can do what the broadest one needs. Move the key one level down, to the tool, and its reach becomes that tool's job. Then split each tool's job into the part that reads and the part that writes, because those are two very different risks.

LiveWhy the credential belongs to the tool2 min▶

A key's reach becomes one tool's job. The agent is a router: it decides which tool to call. The tool is the thing that actually talks to Gmail or to payments. Put the credential on the tool and the question "what can this key do?" has a short answer you can read off the tool's purpose. The tickets tool reads and answers support mail; its key has no business touching payouts.

You can revoke one without the rest. If the refunds tool's key leaks into a trace, you kill that key and the other four tools keep working. Session 1's shared key could not be revoked alone. Session 4 makes revocation fast; this session makes it narrow.

It is the precondition for everything else. You cannot cut scopes on a key that five tools share, because the cut has to satisfy the greediest of them. Separate keys first, then cut each one.

LiveThe read and write split, as OWASP LLM06 names it2 min▶

OWASP's LLM06:2025 Excessive Agency names three root causes: excessive functionality, excessive permissions and excessive autonomy. Its example of excessive permissions is exactly this split: a tool with write or delete rights on a downstream system when it only needs to read.

Its worked scenario fits Halyard closely. An email-summary assistant uses a plugin that can read mail, but the plugin can also send. A poisoned email uses indirect prompt injection to make the assistant forward the inbox to the attacker. OWASP's fix has three parts: a read-only extension, a read-only OAuth scope, and the user approving each send.

Halyard's tickets tool genuinely has to send replies, so it cannot be read-only. That is why the figure draws its two keys separately: the read half (gmail.readonly) and the write half (gmail.send) carry different risks, and session 5 puts a person in front of the write half. Writing them as two lines in the scope table is what makes that possible.

Self-studyBench preview: separate keys alone barely move the number2 min▶

On the bench, switching Credentials from the shared key to "One per tool" and changing nothing else takes the headline from 19 to 15 sensitive actions reachable from a poisoned input, and the weighted blast radius from 121 to 90 (weights are constructed). GitHub drops out, because no tool's key reaches it any more.

But the shortest injected path still ends at change the payout bank account. Each tool now has its own key, yet each key is still its provider's broadest one, so the refunds tool can still do what the payments admin can do. One key per tool limits where a leak spreads; it does not limit what each key opens. That is Part 2's job, and the build-along's.

Real world

OWASP's prevention list reads like a scope table. LLM06:2025 (read 2026-11-10) tells you to minimise extensions, minimise extension functionality and minimise extension permissions, and to avoid open-ended extensions where a narrow one would do. It also notes that logging, monitoring and rate limiting limit the damage but do not prevent it. Halyard's fetch tool is the open-ended one, and it holds no credential at all.

Part 2 · covers fine-grained scopes from real scope lists

Reading the real scope lists

6 min live

"Least privilege" is easy to say and hard to type, because you can only grant what the provider lets you name. So read each provider's list from the coarse end down, and stop at the lowest rung that still does the job. Every provider draws its ladder differently, and some ladders have a rung missing exactly where you need one.

LiveGoogle: Gmail scopes come with Google's own risk class2 min▶

Google's Gmail scope page (read 2026-11-10) tags each scope with its own class. https://mail.google.com/ is full Gmail, including permanent delete that bypasses the trash: Restricted. gmail.modify reads, composes and sends but cannot permanently delete: Restricted. gmail.readonly reads messages and settings: Restricted. gmail.send sends only: Sensitive. Drive has a Non-sensitive rung, drive.file, limited to files the user opens with or shares to the app.

Two things are worth noticing. Reading mail is classed higher than sending it: a read scope exposes everything already in the inbox. And Google's master scope list advises choosing non-sensitive scopes where possible, noting that sensitive scopes require Google's review. The Calendar scope page states no class at all, so for Calendar you judge the rung yourself.

Halyard's tickets tool lands on gmail.readonly plus gmail.send: one Restricted and one Sensitive scope, instead of one Restricted scope that can delete the inbox.

LiveSlack: the difference between chat:write and chat:write.public2 min▶

In Slack's scope reference, chat:write sends messages as the app, in conversations it has been added to. chat:write.public adds the ability to send to public channels the app is not a member of. That one suffix is the difference between "the agent posts in #ops-alerts, where you put it" and "the agent posts in #finance, or anywhere else a poisoned ticket names".

Two more to look for when you inherit a Slack app. users:read.email exposes every person's email address in the workspace, a ready-made target list for a phishing run. admin administers the workspace. Halyard's chat tool needs channels:history to read the channels it was added to and chat:write to post there. Nothing else.

Self-studyGitHub: one permission name, two levels2 min▶

GitHub's fine-grained personal access tokens grant each permission at one of two levels, read or read and write, and write includes read. The permissions page lists 76 names: 32 for a repository, 30 for an organization and 14 for an account. Each REST endpoint is mapped to the level it needs, for example reading a file needs Contents (read) and creating an issue needs Issues (write).

The ladder here is not a chain of nested scopes; it is a grid. You pick the names, then the level for each. The dangerous cells are easy to spot once you look: Administration write can delete or rename a repository, Secrets write can overwrite the Actions secrets a pipeline trusts. For Halyard the right answer is simpler still. No tool needs GitHub, so the right token is no token, which is what one key per tool gave us for free.

Self-studyStripe's restricted keys, the model for Halyard's payments scopes2 min▶

Stripe's restricted API keys page (read 2026-11-10) shows a clean shape. A restricted key starts rk_live_ or rk_test_; a full secret key starts sk_ and opens everything. On a restricted key every resource is set to None, Read or Write, the default is None, and Write implies Read. GET calls need Read; POST and DELETE need Write. Stripe recommends restricted keys over secret keys, especially for AI agents, with one restricted key per service.

Halyard's payments scope names are constructed on that shape, so treat them as a design, not a vendor's list: charges:read, refunds:write:capped (refunds up to 200 USD), refunds:write (any amount) and payouts:admin (including the payout bank account). The refunds tool gets the first two. The exact Stripe label for its refunds permission was not confirmed at source, so check your own provider's list before copying a name.

The honest gap: gmail.send cannot restrict recipients. Gmail has no scope for "send only to the customer who wrote in". The scope picks the verb; it cannot pick who receives the mail. So the cut tickets tool can still send a reply to any address a poisoned ticket names, and the bench will show exactly that as the last path left. When the ladder runs out of rungs, the next control is a person, and that is session 5.

Part 3 · covers expiry and audience

Expiry and audience: a scope also has a when and a where

4 min live

A scope says what a token may do. It says nothing about until when, or at which server. A narrow scope on a token that never expires and is accepted everywhere is still a good find for an attacker. Two more fields close that: an expiry, so a stolen copy goes stale, and an audience, so a copy presented anywhere else is refused.

LiveAudience: RFC 8707's resource parameter2 min▶

RFC 8707, Resource Indicators for OAuth 2.0 (February 2020), adds a resource parameter to the token request. It tells the authorization server which protected resource the client means to use the token with. The value must be an absolute URI and must not contain a fragment. The authorization server should then audience-restrict the token, for example with an aud claim in a JWT, so the token fails at any other resource.

If the resource is invalid, unknown, malformed, or does not fit the requested scopes, the server answers invalid_target. The MCP authorization specification (revision 2026-07-28) makes this mandatory for MCP: clients must send resource set to the MCP server's canonical URI, and servers must check that a token was issued for them. Session 4 builds the broker that does this on Halyard's behalf.

What it prevents, concretely: a token minted for the tickets server, copied out of a trace or replayed by a malicious server, is refused by the warehouse server, because its aud names someone else.

Self-studyMCP's scope minimisation guidance2 min▶

The MCP Security Best Practices page (2026-07-28 docs) has a section on scope minimisation. It warns against wildcard or omnibus scopes such as *, all or full-access, and suggests starting with a minimal initial scope, its example is mcp:tools-basic, then elevating step by step when a tool actually needs more.

The authorization specification gives that step-up a shape: a server that receives a token with too little scope answers 403 with error="insufficient_scope", should say in WWW-Authenticate which scope it wants, and the client asks again for the union. A scope table plus step-up means the agent starts every run on the low rungs and climbs only when a call demands it, visibly.

Self-studyExpiry in practice: one example from Vault1 min▶

Expiry is easiest when the system issuing the credential sets it. In HashiCorp Vault every dynamic secret has a lease with a TTL, and its database secrets tutorial configures a role with default_ttl=1h and max_ttl=24h. That is one way to get expiry; session 4 goes deep on leases, short-lived tokens and the broker. For the scope table tonight, the point is only that every row gets an expiry, and fifteen minutes is the constructed value Halyard writes down.

Two neighbours, two different questions. The warehouse role behind wh.read.aggregates is a warehouse design question, taught in learn-data-access-control, role hierarchy. And which documents a retrieval step may read for a given user is a read filter, taught in learn-ship-internal-ai-assistant, permissions inside retrieval. Here we scope actions: which calls a tool's credential lets it make.

Build-along

Cut Halyard's scopes tool by tool

★ 22 min · everyone builds

The bench starts on rung 1: one credential per tool, each still its provider's broadest. You will cut one tool at a time to the rung from Part 2 and write down what the graph search prints after each cut, so you can see which tool was carrying the most risk. Then you write page 3 of the access plan. All numbers are computed on the constructed Halyard graph, with constructed weights.

Read rung 1 before touching anything. The bench prints 15 of 19 sensitive actions reachable from a poisoned input with no human in the way, a weighted blast radius of 90 (constructed weights), and a stolen key reaching 14. The lesson is not the number; it is that one role can undo a cut without anyone touching the agent.

Homework

Before session 4

30 min
  1. Split your agent's key by tool. For your own agent, list each tool and the credential it would hold on its own. Mark any tool that needs no credential at all.
  2. Read one provider's list from the top. Pick one tool, open its provider's real scope list, and write the rungs from coarse to fine. Circle the lowest rung that still does the job.
  3. Find one honest gap. For one write scope, write what it cannot restrict (recipients, amounts, channels). That gap is a candidate for a gate in session 5.
  4. Add expiry and audience. For each row of your scope table, write how long the credential lives today and which server would reject it if it were replayed. "Never" and "none" are honest answers; write them down.
Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · Halyard moves from one shared key to one credential per tool, changing nothing else. What does the bench print?

Separate keys take the headline from 19 to 15 and remove GitHub, because no tool's key reaches it. But each tool still holds its provider's broadest key, so the refunds tool can still change the payout bank account. Separate keys limit where a leak spreads; scopes limit what each key opens. D overstates it: GitHub does drop out.

2 · The tickets tool must send replies to customers. Which real Gmail scope lets it send, and nothing more?

gmail.send sends only, and Google classes it Sensitive. https://mail.google.com/ is full Gmail including permanent delete that bypasses the trash. gmail.modify cannot permanently delete, but it also reads and changes the whole mailbox, far more than sending. gmail.readonly cannot send at all; Halyard pairs it with gmail.send for the reading half.

3 · Halyard's tickets token carries aud = https://mcp.halyard.example/tickets. What does the audience check prevent?

RFC 8707's resource parameter lets the authorization server bind the token to one resource, so any other resource refuses it. B is expiry, a separate field. A is the recipient gap that no Gmail scope closes. C is injection steering the agent to a tool it is allowed to call; audience does not stop that, gates do.
