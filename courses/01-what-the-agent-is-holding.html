What the agent is holding

You gave an agent tools, and every tool needed a key. The agent now holds credentials the way a service does, but it reads text from strangers all day and decides for itself what to call next. Tonight we treat the agent as what it is, a non-human identity, follow its keys to the five places they end up, price the shared admin key almost every first build ships with, and count the blast radius of a real-shaped setup on a bench that searches the graph in your browser.

Part 0

Where we start

The running case is a constructed Halyard example. Halyard is an invented mid-size logistics SaaS. Its platform team has shipped one internal ops agent: it reads support tickets and customer email from a shared Google Workspace inbox, queries the analytics warehouse, issues refunds up to a limit, posts to the team's Slack, and fetches the tracking pages customers paste into tickets. Each capability is a tool behind an MCP server. On day one every tool reads the same secret, HALYARD_ADMIN_KEY, from an environment variable. The question for all six sessions: if this agent reads one poisoned ticket tomorrow, what can it reach, with whose authority, and could you prove afterwards what it did?

Part 1 · covers non-human identity and the OWASP NHI Top 10

An agent is a non-human identity with opinions

5 min live

A cron job, a CI pipeline and a payments integration all hold keys. Security teams call them non-human identities and manage them as a class. An agent belongs to that class with one difference that changes everything: it chooses its own next call based on whatever text it just read. How the agent loop picks a tool is taught in learn-ai-agents, your first tools; here we look only at the keys behind those tools.

LiveWhy an agent is a new kind of non-human identity3 min▶

A service account does what its code says. If a billing script holds a payments key, you can read the script and list every call it will ever make. The key's risk is the script's behaviour plus the chance the key leaks.

An agent does what its context suggests. The same payments key behind a refunds tool is now driven by a model that reads ticket text written by anyone with an email address. You can no longer list its calls by reading code; you can only bound them by what its credentials allow. That is why this subject is about the keys and not the prompt: the prompt is a request, the credential is the limit.

Treat it as a workload with an owner. The agent gets its own entry in your identity inventory, with a named human owner, the same as any service. Session 2 decides whose authority each call should carry.

Real world

A payments provider now says it out loud. Stripe's restricted API keys page (read 2026-11-10) recommends restricted keys over full secret keys, and singles out AI agents as a case for them, with one restricted key per service. A restricted key starts rk_ and grants None, Read or Write per resource; a full secret key starts sk_ and grants everything. Halyard's refunds tool is holding the second kind.

Part 2 · covers where an agent's credentials end up

The five places an agent's key ends up

6 min live

A service's key sits in one place and is read by code. An agent's key travels. It starts in the environment, and from there it can be copied into four more places, each with a different reader. Once a key is in the context window, the model can repeat it, and anything the model can say, an attacker who controls its input can ask it to say.

LivePlaces 1 to 3: environment, prompt, tool output3 min▶

1. The environment variable. The normal home of a service key, and the default the MCP specification describes for local servers: an MCP server running over STDIO "SHOULD NOT" use the HTTP authorization flow and instead retrieves credentials from the environment (specification revision 2026-07-28, read at source). Fine, as long as nothing copies the key out of it.

2. The prompt or context. Someone pastes the key into the system prompt so the model can "call the API directly", or a tool that reads config files returns one. The model now has the key as text. OWASP's LLM02:2025 Sensitive Information Disclosure lists security credentials among the sensitive information a model can disclose.

3. Tool output echoed back. The quiet one. A tool fails and returns its own error, and the error contains the connection string or the key prefix it tried. Tool results go straight into the context, so a key the agent was never meant to see is now in it.

LivePlaces 4 and 5: traces, and the provider's side3 min▶

4. Logs and traces. Agent observability tools record every tool call with its arguments, and an HTTP client logged at debug level records headers. A bearer token in an Authorization header is now in a log store that the whole on-call rotation can search.

5. The model provider's side. Everything in the context window is sent to the model provider on every turn. What happens to it there is set by your contract and the provider's data policy, which you should read for retention and review terms. A key that reached place 2 or 3 has also reached place 5.

The fixes are session 4's subject: a broker that attaches the key at call time so it never enters the context, redaction before anything is traced, and short-lived keys so a copy that does leak expires.

Search for the key, not the agent. Take a key's first eight characters and search your trace store, your agent transcripts and your tool error logs for them. Every hit is a place the key went that your design did not mean it to.

Part 3 · covers why one shared admin key is the default

Why the shared admin key ships first, and what it costs

4 min live

Nobody designs a shared admin key. It is what you have when the demo has to work by Friday: one secret, already in the vault, already trusted by every system. It is the right call for a prototype and the wrong one for anything that reads text from customers, for three reasons you can draw.

LiveThe three costs of one shared key3 min▶

You cannot revoke it alone. When the agent's key leaks you want to kill the agent's access in seconds. If the deploy script and the billing job hold the same key, revoking it is an outage across all of them, so in practice nobody revokes it. OWASP calls this NHI9, reuse.

You cannot attribute it. Every action is logged under the same credential. When a refund goes wrong, the log says the key did it, and the key belongs to everyone. Session 6 builds the audit record that fixes this.

It opens everything. The key can do whatever its most powerful consumer needed, so a poisoned ticket can steer the agent to any of it, and if the key itself leaks, the attacker gets the rest with no agent and no gate in the way. That is the number the build-along counts.

Self-studyRotation is a different problem, taught next door2 min▶

How to rotate a warehouse password, issue short-lived credentials to machines and run service accounts at least privilege is covered in learn-data-access-control, secrets and keys, and the estate-wide view of human and service credential paths in learn-cyber-security, credential paths. Here we keep to what is specific to agents: keys reachable from a model's context, tool output and traces, and actions a model chooses on its own.

Build-along

Inventory Halyard's keys, then count the blast radius

★ 22 min · everyone builds

First on paper, then on the bench. Write the inventory for Halyard's (constructed) ops agent with the steps below; if you have your own agent, inventory that too and keep Halyard as the worked answer. Then load the day-one setup on the bench and read what a graph search says a poisoned ticket can reach.

List every key the agent can reach. Not just the ones the agent "uses": every credential readable from its process, its config and its tools. For each, write where it lives and who else holds it.

Write what the key opens, per system. Look up the admin scope on each provider. This is the part teams skip, and it is where GitHub turns up.

★ Step 2 · what HALYARD_ADMIN_KEY opensGmail https://mail.google.com/ full mail, incl. permanent delete Slack admin, chat:write.public, workspace admin, any channel users:read.email warehouse wh.admin export, drop (constructed role) payments payouts:admin refunds of any size, payout bank account (constructed) GitHub Contents, Secrets, push, overwrite CI secrets, Administration: write delete a repository

Mark the five places. For the key, write yes, no or unknown for each place from Part 2. "Unknown" counts as yes until you have searched.

★ Step 3 · where the key has been1 env var yes 2 prompt or context unknown (search transcripts for hx_live_) 3 tool output YES: the warehouse tool's 401 error prints it 4 logs and traces YES: debug tracing records headers 5 provider side yes, wherever 2 or 3 is yes

Run the bench on day one. The bench below starts on rung 0, one shared admin key. Read the headline, the weighted blast radius and the shortest injected path. Then switch Credentials to "One per tool" and watch which actions drop out, and which do not.

Write the baseline into the plan. Copy the numbers the bench prints, not your guess. On the day-one setup it prints 19 of 19 sensitive actions reachable from untrusted input with no human in the way, a weighted blast radius of 121, and a shortest injected path of three hops: ticket body, ops agent, refunds tool, change the payout bank account. A stolen copy of the key reaches 18 of them directly, including four GitHub actions no tool exposes.

★ Step 5 · baseline, top of the access planDay one (bench rung 0): 19 of 19 sensitive actions reachable from a poisoned ticket, email or web page, no gate. Weighted blast radius 121 (constructed weights). Worst path: ticket -> agent -> refunds tool -> payout bank account, 3 hops. A stolen key alone reaches 18, incl. GitHub. Target for session 6: show the number falling, rung by rung.

The one-per-tool switch is a trap worth falling into. On the bench it takes the headline from 19 to 15 and removes GitHub entirely, which feels like progress. But each tool still holds its provider's broadest key, so the agent can still change the payout bank account in three hops. Separate keys are the precondition for cutting scopes, which is session 3.

Homework

Before session 2

30 min
  1. Inventory your own agent. Every credential its process, config and tools can read, where each lives, and who else holds it.
  2. Search for one key. Take the first eight characters of one agent key and search your traces, transcripts and error logs. Write down every place it appears.
  3. Find your GitHub. For each key, list one thing it opens that the agent never needs. That list is your free blast-radius reduction.
  4. Mark each tool call by trigger. For each tool, write whether the agent calls it on its own (a queue, a schedule) or because a named person asked. Session 2 needs this.
Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · On Halyard's day-one setup, which of these can the shared key reach even though no tool of the agent exposes it?

A, C and D are all reachable through the agent's own tools. GitHub is reachable only because the key is shared with the deploy scripts: an attacker who gets a copy of the key can call GitHub directly. You find that door by inventorying the key, not the agent.

2 · The warehouse tool fails and returns "401: bad key hx_live_9f2c...". Why is this worse than the key sitting in the environment variable?

In the environment the key is read by code. In the context it is text the model can say, and a poisoned ticket can ask it to say it somewhere useful to the attacker. It also reaches places 4 and 5. B and D are not true in general.

3 · On the day-one setup, what does the bench report as the shortest injected path to the heaviest action a poisoned ticket can reach?

The payout bank account carries the highest constructed weight (10) among actions the agent's own tools can reach, and the refunds tool holds the shared key, so three hops get there. C is the hope that prompt injection does not happen; the bench assumes it does. GitHub is reached only by a stolen key, a longer path.
