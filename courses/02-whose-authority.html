Whose authority: the agent's own, or the user's

Every tool call carries somebody's authority. Sometimes it should be the agent's own, because a queue fired and nobody asked. Sometimes it should be the person who typed the request, and then the agent must carry that person's narrower reach instead of its own. Tonight we draw both models, read the token exchange that lets an agent act for a person without pretending to be them, draw the confused deputy that happens when nobody decides, and map each of Halyard's five tools to one identity model.

Where we pick up

The running case is a constructed Halyard example. Halyard is an invented mid-size logistics SaaS whose ops agent has five tools: tickets on a Gmail support inbox, the analytics warehouse, refunds, chat on Slack, and fetch for the tracking pages customers paste. Session 1 found one shared key, HALYARD_ADMIN_KEY, behind all of them, and a log where every line says the key did it. Before cutting any scope we need to answer a prior question for each tool: when this call happens, whose authority is it spending? Some calls start from a queue with nobody behind them. Others start because support lead Dana (constructed) typed a request in chat.

Part 1 · covers service identity against acting for a person

Two ways to hold authority

5 min live

An agent can hold authority in two ways, and both are legitimate. It can act as itself, a workload with its own identity, the way a nightly job does. Or it can act on behalf of a person, carrying a token that says who asked and limits the agent to what that person may do. The mistake is not picking the wrong one. The mistake is never picking, so the agent spends one big credential on everything. How the agent loop decides to call a tool at all is in learn-ai-agents, your first tools; here we decide what that call is allowed to carry.

LiveWhen each model is right3 min▶

The agent's own identity, for work nobody asked for. A new email lands and the agent triages it. A schedule fires and it builds the morning delivery report. It posts a status update to the ops channel. No person is behind these calls, so there is no person's authority to borrow. The agent should hold its own identity, scoped to the job, with a named human owner in the inventory.

A person's delegated authority, for work a person asked for. Dana types "refund the customer on ticket 4471" in chat. Now a named person is behind the call, and the call should be limited to what Dana herself may do. If Dana cannot refund above her limit, neither can the agent acting for her, and the log can say Dana asked.

The rule in one line. If a named person asked, carry their authority. If nobody did, the agent acts as itself. Write it at the top of the identity map and apply it per tool, and per trigger when one tool has both.

Mixing them up fails in both directions. Run Dana's refund on the agent's own identity and the agent can do more than Dana could, with nothing in the log naming her. Run the morning report on some engineer's token and the report breaks the day they leave, which is OWASP's NHI10 in reverse: a machine running on a person.

Self-studyWorkload identity: SPIFFE IDs and SVIDs4 min▶

SPIFFE is an open standard for giving workloads, not people, a verifiable identity (concepts page, read at source 2026-11-10). Four ideas carry over to an agent directly.

  • The SPIFFE ID is a URI, spiffe://trust-domain/workload-identifier. The trust domain is the root of trust; SPIFFE notes that staging and production generally sit in separate trust domains, which is NHI8 environment isolation done by design.
  • The SVID, the SPIFFE Verifiable Identity Document, carries exactly one SPIFFE ID and is signed by the trust domain's authority.
  • Two formats. An X.509-SVID is a certificate used for TLS and is the preferred form; a JWT-SVID is a token, useful through layer 7 proxies, with the caveat SPIFFE gives that tokens can be replayed.
  • Short-lived, rotated automatically. The Workload API hands a workload its ID, private key, SVID and trust bundles without the workload needing a pre-existing secret, and the keys are short-lived and rotated, so a copy that leaks stops working soon.

For Halyard (constructed), the ops agent becomes spiffe://halyard.test/ops-agent. That replaces "whoever holds HALYARD_ADMIN_KEY" with one identity that belongs to one workload and can be revoked without touching the deploy scripts. You do not need SPIFFE specifically: any workload identity with these four properties does the job. The human and service credential paths across the rest of the estate are mapped in learn-cyber-security, credential paths.

Self-studyZero trust says decide per session, on identity2 min▶

NIST SP 800-207, Zero Trust Architecture (August 2020, read at source), lists seven tenets in section 2.1 and presents them as ideal goals rather than a checklist every system can meet. Two of them are the reason to give an agent its own identity at all.

  • Tenet 3: "Access to individual enterprise resources is granted on a per-session basis." Being authenticated to one resource does not grant another. For an agent: holding the tickets credential must not open the warehouse.
  • Tenet 4: access is decided by dynamic policy that includes client identity, user or service, along with the application, asset state and behavioural and environmental attributes. For an agent: the policy can only tell "the agent on its own" from "the agent for Dana" if the request says which one it is.

A shared admin key defeats both. It is one session that opens everything, and it carries no identity a policy could tell apart.

Real world

A workload name you can read. The SPIFFE concepts page gives spiffe://acme.com/billing/payments as its example ID: trust domain acme.com, then a path that names the workload. Nothing in it names a person, and nothing in it is a secret. The secret is the short-lived key behind the SVID that proves the name, and that key rotates on its own.

Part 2 · covers delegated OAuth and token exchange (RFC 8693)

Token exchange: subject, actor, and the act claim

6 min live

When Dana asks for a refund, the agent holds two things: Dana's token from the chat sign-in, and its own identity. Neither is the right thing to send to the refunds server. Dana's token was not issued for that server, and the agent's own identity carries no trace of Dana. OAuth 2.0 Token Exchange, RFC 8693, is the standard swap: present both, and get back one new token, for one resource, that names both parties.

LiveThe request: subject, actor, and what you ask for2 min▶

RFC 8693 (January 2020, Standards Track, read at source) defines one grant, grant_type=urn:ietf:params:oauth:grant-type:token-exchange, posted to the authorization server's token endpoint.

  • subject_token is required. It represents the party on whose behalf the new token is requested: Dana. Its subject_token_type is required too.
  • actor_token is optional. It represents the party doing the acting: the agent. If you send it, actor_token_type becomes required.
  • requested_token_type is optional. Leave it out and the authorization server chooses.
  • Target the resource. The request can name the one server the new token is for, so the token that comes back is useless anywhere else. Session 4 makes that audience binding a MUST through the MCP specification.
Token exchange request and the token it returns (fake values, read, not run)POST /oauth/token HTTP/1.1 Host: auth.halyard.test Content-Type: application/x-www-form-urlencoded grant_type=urn:ietf:params:oauth:grant-type:token-exchange &subject_token=eyJhbGciOi...dana &subject_token_type=urn:ietf:params:oauth:token-type:access_token &actor_token=eyJhbGciOi...opsagent &actor_token_type=urn:ietf:params:oauth:token-type:jwt &resource=https://refunds.halyard.test/mcp # decoded payload of the issued token { "iss": "https://auth.halyard.test", "aud": "https://refunds.halyard.test/mcp", "sub": "dana", "act": { "sub": "halyard-ops-agent" }, "scope": "refunds:write:capped", "exp": 1794316500 }
LiveImpersonation or delegation: can the server tell?2 min▶

RFC 8693 names two semantics, and the difference is exactly the one that matters for an agent.

  • Impersonation. The actor is treated as the subject. The issued token says Dana, and the recipient generally cannot tell Dana from the agent acting as Dana. Every refund looks like Dana clicked it.
  • Delegation. The actor keeps its own identity and acts as an agent for the subject. The token says Dana is the subject and carries an act claim naming the agent. Actions are attributable to the agent, on Dana's behalf.

For an AI agent, choose delegation. The whole point of the identity map is that a log line can later say "the agent did this because Dana asked", and impersonation erases the first half of that sentence. Session 6 builds the audit record on this claim.

Self-studyChains, may_act, and which claims decide3 min▶

Nested act is a delegation chain. If a triage agent hands work to the ops agent, the ops agent's token can carry an act naming itself as the current actor, with a nested act inside it recording the triage agent as the prior one. The chain is history, not permission.

Nested act: current actor outside, prior actor inside (fake values)"sub": "dana", "act": { "sub": "halyard-ops-agent", "act": { "sub": "halyard-triage-agent" } }

Decisions use the top level and the current actor only. RFC 8693 says access decisions are made on the top-level claims and the current actor; the nested actors are informational. A server that grants something because a prior actor in the chain was trusted is reading the claim wrong.

may_act says who is allowed to act. A token can carry a may_act claim asserting which party is authorised to act for the subject. On Dana's chat token, may_act naming halyard-ops-agent is how the authorization server can know, before it exchanges anything, that Dana's token may be used by this agent and by nothing else.

Self-studyThe IETF agent drafts: drafts, not standards2 min▶

Several Internet-Drafts try to profile OAuth for AI agents. Two were read at source on 2026-11-10. Both are drafts, not standards, and neither should be cited as settled practice.

  • draft-oauth-ai-agents-on-behalf-of-user-02 (2025-08-25, individual submission, now expired). It extends the authorization code flow with a requested_actor parameter in the authorization request and an actor_token in the token request, aiming for explicit consent and an auditable user to client to agent chain in the token claims.
  • draft-klrc-aiagent-auth-03 (2026-07-06). It defines no new protocol; it maps existing OAuth and WIMSE standards onto agents and names the gaps. It was adopted by the WIMSE working group and replaced by draft-ietf-wimse-aims, which was not read here: check its current revision before you cite it.

What to take from them today: the people writing standards are converging on the shape drawn above, a subject, an actor and a claim naming both. Drafts change or expire before anything is standardised, as the first one already has, so build on RFC 8693 and keep any draft-specific fields behind an adapter.

Real world

The standard is older than the agents. RFC 8693 was published in January 2020, years before tool-calling agents, for services that call other services on a user's behalf. Its authors already drew the line we need: impersonation, where the recipient cannot tell, against delegation, where the act claim keeps the actor visible. Agents did not need a new idea, only the discipline to use the old one.

Part 3 · covers the confused deputy

The confused deputy, drawn

4 min live

A confused deputy is a program that holds authority and is tricked into using it for someone else. An agent with one big key is the textbook case: it holds more authority than anyone who talks to it, and it reads requests from all of them in the same context. Dana asks for one refund. The ticket she points at asks for another. The agent cannot tell whose request is whose, and it has the key for both.

LiveWhy an agent is the textbook confused deputy2 min▶

The classic definition. A confused deputy is a program with authority of its own that is tricked by a less privileged party into using that authority on the party's behalf. The deputy is not malicious; it simply cannot tell which of its callers a request came from, and it acts with everything it holds.

An agent fits it exactly. Dana's instruction and the ticket text arrive in the same context window as the same kind of thing: tokens to read. If the agent holds Halyard's payments key, it can issue any refund the key allows, so the attacker borrows the agent's authority by writing into a ticket. Neither Dana nor the attacker could have issued the 190 USD refund to customer B themselves. The deputy could.

The fix is to shrink what the deputy holds per call. For rep work, the agent spends only the exchanged token, so the refund is bounded by Dana's own rights. For queue work, the agent spends only its own identity, and that identity has no refund scope at all. This is the identity map's job.

LiveMCP's own confused-deputy case2 min▶

The MCP Security Best Practices page (2026-07-28 documents, read at source) describes a confused deputy at the OAuth layer, which is worth knowing because it is the same shape one floor down.

  • The setup. An MCP proxy server talks to a third-party authorization server using one static client id. It also lets MCP clients register dynamically, and the third-party server remembers consent with a cookie.
  • The attack. An attacker registers a client with a malicious redirect_uri. Because the consent cookie is already set from the user's earlier visit, the consent screen is skipped, and the authorization code is sent to the attacker.
  • The mitigations. Proxy servers MUST obtain consent per client and keep a per-user registry of approved client ids, match redirect_uri exactly, and use a single-use, short-lived state value.

Same lesson: the proxy held authority (the static client id and the user's standing consent) that it spent for a party who never earned it.

Self-studyThe honest caveat: on-behalf-of narrows reach, not injection2 min▶

Carrying Dana's authority caps the agent at what Dana may do. It does not stop a poisoned ticket from steering the agent inside that cap. If Dana is allowed to refund customer B, and the agent reads the ticket while working on Dana's request, the injected refund is a perfectly valid request under her token. The server will check sub, act and aud, and all three will pass.

So on-behalf-of is a reach control, not an injection control. It removes everything above Dana's rights from the poisoned path; what is left needs the other layers: tighter scopes in session 3, keys out of the context in session 4, and a person's approval on the irreversible actions in session 5. Session 6 runs the finished design with this exact drift switched on, rep requests that also read the ticket text, and shows what the bench prints for it. Testing whether the injection itself succeeds is the red team's job, in learn-ai-red-team, prompt injection.

Real world

The protocol names the problem in its own security page. The MCP Security Best Practices page for specification revision 2026-07-28 lists the confused deputy among its attacks and makes per-client consent a MUST for proxy servers. When the protocol your agent speaks writes the confused deputy into its normative text, it is not a theoretical risk.

Homework

Before session 3

30 min
  1. Map your own agent. One row per tool: who triggers it, whose authority it should carry, and the credential that would carry it. Apply the one-line rule and note any tool where the answer surprised you.
  2. Find one impersonation. Look for a place where your agent calls a system with a person's token and nothing in the request names the agent. Write what the receiving log would show for one call.
  3. Decode one real token you own. Take a token from a test environment you control, decode its payload locally, and write down its aud, sub and whether it has an act. Never paste a live token into an online decoder.
  4. List each tool's widest permission. For every row of your map, write the broadest scope the credential holds today. Session 3 cuts that list to the job.
Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Halyard's agent builds the morning delivery report on a schedule, and also issues a refund when Dana asks in chat. Which identity model fits each?

Nobody asked for the scheduled report, so there is no person's authority to carry, and borrowing Dana's would break the day she leaves. Dana asked for the refund, so the call should carry her authority and be capped at her rights. B is the shared-key habit; it lets the refund do more than Dana could.

2 · A token presented to the refunds server has sub: dana and act: { sub: halyard-ops-agent }. What does the act claim record?

RFC 8693 delegation keeps the actor visible: sub is the party on whose behalf the call is made, act names the party doing it. Impersonation would hand over a token that just says Dana. C is the job of aud; D is an approval, which is session 5.

3 · Halyard runs every rep refund on the rep's exchanged token. A rep asks for a refund on a ticket whose text also asks for a refund to a different customer, one the rep is allowed to refund. What happens?

On-behalf-of removes everything above the rep's own rights from the poisoned path, which fixes the confused deputy's surplus authority. Inside those rights, the injected request is valid: aud, sub and act all pass. Closing that needs a person's approval on the refund, session 5. B is true for queue work, not for a rep's request.
